# HearthSocial.ai — Progress Tracker

*(Previously called "Role-Play App" — the `roleplay_app/` folder name and internal references from that era are unchanged.)*

Local AI companion chat app per `DESIGN.md`, built in this `roleplay_app/` folder (the rest of the parent directory is an unrelated older prototype — untouched). Full architecture/design rationale lives in the approved plan at `C:\Users\sachm\.claude\plans\tranquil-swimming-sphinx.md`; this file tracks build status and decisions made since.

## Stack

- **Backend**: Python/FastAPI (`roleplay_app/backend/`), reusing the root venv at `c:\Users\sachm\Downloads\mistral-12b`.
- **Frontend**: Vite + React (`roleplay_app/frontend/`), built and served directly by the backend — one port, no separate dev server needed in normal use (see "Running it" in `README.md`).
- **Inference**: `llama-server.exe` (`C:\Softwares\llama-cpp-vulkan\`) over its OpenAI-compatible HTTP API, model `gemma-4-E4B-it-uncensored-Q4_K_M.gguf`.
  - Launch: `-c 16384 -np 1 -ngl 999 -fa on -ctk q8_0 -ctv q8_0 --host 127.0.0.1 --port 8080`
  - Single slot deliberately, not two: measured ~15.7GB total RAM, only ~1.86GB free with the model loaded, so summarization shares the chat slot rather than running on a genuinely concurrent second one (see Decisions below).
- **Storage**: SQLite + `sqlite-vec` extension (`roleplay_app/backend/data/app.db`).
- **Embeddings**: `BAAI/bge-small-en-v1.5` (384-dim), loaded fully offline (`HF_HUB_OFFLINE=1`) once cached.
- **Fonts**: Manrope + Cormorant Garamond, downloaded and served as local `.ttf` files (`frontend/public/fonts/`) — no Google Fonts CDN dependency, fully offline.

**Social feed** lives in `routers/feed.py` plus one table in `db.py`: `feed_posts` (character-scoped, not session-scoped — a character's public presence survives clear-chat, unlike `summaries`). Helpers: `shared.get_current_state()` (active-session summary, falling back to the character's `initial_state` if it's never started a chat), `_build_feed_post_messages()` / `_build_feed_reaction_messages()`. New directive constant in `character_state.py`: `FEED_POST_STYLE_DIRECTIVE` (deliberately separate from `RESPONSE_STYLE_DIRECTIVE` — plain first-person text, no `*action*`/`(monologue)` formatting).

**Generated images** (`routers/images.py`) use one table, `generated_images` (`db.py`): nullable `message_id`/`feed_post_id` FKs with a `CHECK` requiring at least one, and a *partial* unique index on each (`WHERE ... IS NOT NULL`) so at most one image exists per message/post — regenerating deletes the old row and overwrites the same deterministic filename (`msg-{id}.jpg` / `post-{id}.jpg`) rather than accumulating files.

**Current tuned config** (`config.py`): `GENERATION_HEADROOM_TOKENS=1024`, `SUMMARIZE_EVERY_N_MESSAGES=10`, `MAX_STAT_DELTA_PER_CYCLE=10`, `MAX_CHARACTER_MEMORY_CHARS=600`, `NOTABLE_FACTS_CONSOLIDATE_THRESHOLD=12`.

**Relationship stage thresholds fixed** (2026-07-27, `relationship_stages.json`): building the relationship stage map surfaced a real inconsistency - `family` (50 affection/40 closeness) and, to a lesser extent, `taboo` (75/60) had lower thresholds than `confidant` (55/45) despite being drawn as branches that fork *after* confidant. Rebalanced so every post-confidant branch stage now requires strictly more than confidant: `partner` 80/70 (was 70/55), `spouse` 90/85 (was 80/65), `family` 70/65 (was 50/40), `taboo` 85/80 (was 75/60). `summarizer.py`'s numeric gate only enforces a stage's own threshold when its rank (affection+closeness sum) exceeds the stage being left, so the old family/confidant mismatch wasn't letting anyone skip requirements outright - it just meant the gate silently didn't apply on a confidant→family move. Requires restarting the backend to pick up the new `relationship_stages.json` values (loaded once at import time) - discovered the hard way when the new thresholds didn't show up in the UI, since `run.ps1`'s `uvicorn --reload` only watches `*.py` files by default, not `.json`. Fixed by adding `--reload-include "*.json"` to the uvicorn command in `run.ps1`, so future edits to `relationship_stages.json` (or any other `.json` config) now trigger an automatic reload too.

## Features implemented

- Character cards (persona, opening scene trigger, sampling preset, starting stats) — hand-authored JSON or created/edited through the UI (full CRUD, edit button on every card), with optional avatar image upload + crop.
- **Starting affection/closeness derived from starting stage, not free-input** (2026-07-27): `CharacterForm.jsx` no longer has affection/closeness sliders - only a starting relationship-stage dropdown. `routers/characters.py`'s `CharacterIn` model dropped the `character_affection`/`character_closeness` fields entirely; `_card_to_initial_state()` now sets them straight from `character_state.stage_thresholds(relationship_stage)`, so a new character can no longer start inconsistent (e.g. stage "confidant" with affection too low to have actually reached confidant). Applies to both create and edit, since both go through the same function. Hand-authored `characters/*.json` files that set `character_affection`/`character_closeness` directly in `initial_state` are unaffected - this only changes what the UI form and its backend model accept.
- Click a card → hidden trigger message auto-generates the opening scene (never shown to the user, but present in the model's context).
- Structured JSON state per session (location, mood, appearance, memory, affection, closeness, relationship stage, notable facts, relationship history), updated by the summarizer every 10 messages — an LLM merge, not a scoring formula, with defensive parsing (bad output leaves prior state untouched) plus code-level enforcement layered on top (see Anti-drift below).
- **Anti-model-drift enforcement** (added after observing unbounded affection/closeness escalation in real play): per-cycle delta cap (±`MAX_STAT_DELTA_PER_CYCLE`) so metrics can't jump in one summarization pass; a numeric stage gate that blocks/reverts a `relationship_stage` advance unless affection/closeness already clear that stage's threshold; `character_memory` truncated at `MAX_CHARACTER_MEMORY_CHARS` on sentence boundaries; affection/closeness clamped to 0–100 post-parse. All enforced in code, not trusted to the model — a tone-ban instruction ("avoid sacred/profound/destiny") was tried first and empirically failed (see Known gaps).
- **Family/taboo stage disambiguation**: fixed a real bug found via live play - characters whose *persona* establishes a relationship to the user that's inherently forbidden (a parent/child dynamic, or the character already being married/committed to someone else) were advancing to `partner`/`spouse` instead of `taboo`, because `summarizer.run()` never gave the model the character's persona at all - it only ever saw the numeric state JSON and raw transcript, with no way to know the backstory made the romance forbidden. Fixed by loading the persona into the prompt and adding an explicit disambiguation rule. Verified against two real archived/live sessions with different flavors of "forbidden" (Kiara: parent/child; Sansa: already married to someone else) - the first version of the rule only mentioned "blood/family relation" and "power-imbalance" and still picked `partner` for Sansa's case, so the rule was broadened to explicitly name "already married/committed to someone else" too, then re-verified.
- `relationship_history`: ordered log of *why* the relationship stage changed, appended by the summarizer only on an actual (gate-approved) stage transition.
- Two-lever behavior control: plain-language directives (dominant) + small sampling nudges (secondary), both derived from the same state.
- Clear-chat archives the old session and starts a new one seeded from the character's own `initial_state` (not hardcoded zeros) — RAG is a clean slate per session, no cross-session leakage.
- **Hide/unhide**: both characters and individual sessions can be hidden from their respective lists and restored via a PIN-gated modal (`UNHIDE_PIN`, overridable via `ROLEPLAY_UNHIDE_PIN` env var).
- Session history: collapsible panel lists past (archived) sessions plus a separate hidden-sessions sub-list; clicking one shows it read-only with a back-to-current button.
- RAG: session-scoped vector search (`sqlite-vec`, query syntax empirically verified — no `JOIN` in the KNN query, that breaks the LIMIT constraint). Each retrieved fact is tagged with how long ago it was said (recomputed fresh every turn from the seq gap, not a stored/stale label), and the surrounding prompt text explicitly tells the model these are historical and shouldn't override the live `Current state` block.
- **Director's note**: a manual, one-turn out-of-character steering nudge (🎬 toggle in the chat input). Stored as a real message (`hidden_trigger` role, `visible=1` — distinct from the invisible opening-scene trigger which uses `visible=0`) so it renders as a divider in the chat log and gives the model a concrete turn boundary to react to; the OOC framing ("not something the character says or hears") is applied only when building the model's input, not in what's stored/displayed. Works with or without an accompanying user message.
- Per-session sampling parameter override popup (temperature/top_p/top_k/min_p), auto-shown on entering a chat, no server restart needed since these are per-request fields.
- **Manual summarization trigger** (`POST /api/sessions/{id}/summarize`, "🔄 Update memory" in `ChatStatsBar`): fire-and-forget, same `asyncio.create_task(summarizer.run(...))` pattern as the automatic every-N-message trigger, not a blocking request - the frontend just forces an immediate `refreshState()` afterward so the existing "✍️ Summarizing…" badge/poll picks it up right away instead of waiting up to 5s for the next tick. Added because image generation reads `character_appearance`/`location`/`character_mood` from the last-summarized state, which can lag behind the live conversation between automatic summaries - this lets you force a fresh summary immediately before generating a scene image. `summarizer.run()` already no-ops safely if there's nothing new since the last summary or one is already in flight, so the endpoint just checks `latest_seq > last_summarized_seq` before bothering to queue it (returned as `started: bool`).
- **Suggested user reply** (`POST /api/sessions/{id}/suggest-reply`, `routers/chat.py`): generates a plausible next message *for the user to send*, not the character - reads the last 10 visible messages (both roles, widened from an initial 5), asks the model in a system instruction to respond in first person "as if the user is typing it themselves." Deliberately fills the input box rather than sending automatically (confirmed with the user before building - "instead of user" initially read as auto-continue, which would have been a materially different and riskier feature). First version had `ChatInput.jsx` show this button *in place of* Send whenever the input was empty - which broke sending a director's-note-only message (no main text, note has content), since Send simply disappeared. Corrected per explicit user instruction: Send is unconditional again (never hidden), and Suggest is squeezed in *beside* it, shown only when both the main input and the director's note are empty. First prompt version produced flat, generic one-liners with no formatting - rewritten to explicitly reuse the same `*action*`/dialogue/`(monologue)` convention as `character_state.RESPONSE_STYLE_DIRECTIVE` (the one the character's own replies already follow), asking for at least two of the three combined so the suggestion carries real emotional weight instead of a bare line.
- Live stats bar (❤️ affection, 🤝 closeness, 🎭 mood, relationship-stage badge).
- **Relationship stage map** (2026-07-27, `RelationshipStageMap.jsx`): clicking the relationship-stage badge in `ChatStatsBar` slides up a bottom-sheet tracker — a trunk of detail cards (stranger → acquaintance → friend → confidant, icon + name + requirement text + checkmark/"here now" pill) forking after confidant into three branch columns (Romantic: partner → spouse, Family, Taboo), matching `relationship_stages.json`. Rebuilt 2026-07-27 to match the "9a" design option pulled from the `RolePlay UI design directions` Claude Design project (`RolePlay Design Options.dc.html`) via the design MCP - kept 9a's card layout/bottom-sheet chrome but adapted the content to this app's real data: the mockup's fictional 2-way Romance/Rivalry fork became the real 3-way fork above, and its invented narrative subtitles ("shared 3 stories by the fire") became real numeric threshold text ("Cleared affection 35+ · closeness 25+" / "Needs affection 60+ · closeness 45+"), since the app has no per-transition narrative data to draw on. Branch cards get one of four statuses - passed/current/ahead (later stages on the branch you're actually in)/alternate (a branch you're not on) - "ahead" vs "alternate" only being knowable once the session has actually entered a branch; while still in the trunk, all three branches read as "alternate" since there's no signal for which one a session is heading toward. A small progress bar shows live affection/closeness progress toward the next trunk stage (100% once past confidant). `character_state.stage_options()` (`GET /api/stages`) now also returns each stage's `min_affection`/`min_closeness` so the frontend doesn't have to duplicate the threshold numbers.
- Reasoning/thinking block display (collapsible, live-stream only — deliberately **not** persisted to the DB). This surfaced a real regression from the image-generation work: to get a new message's real database id (needed for the "Generate image" button), `ChatView.jsx` was refetching `GET /api/sessions/{id}/messages` after every turn and replacing the whole `messages` array - since that endpoint never returns `reasoning`, the Thinking block vanished within moments of a reply finishing instead of only on an actual page reload. First patched with a `refreshMessagesPreservingReasoning()` workaround that re-attached the in-memory reasoning after the fact; then fixed properly by removing the refetch entirely - `_stream_assistant_reply()` in `routers/chat.py` now yields one more SSE event, `{"type": "message_id", "message_id": <int>}`, right before `[DONE]`, straight from the row it just inserted. `consumeStream()` in `ChatView.jsx` captures and returns that id, and `send()`/`regenerate()` patch it directly onto the last message in state - no network round-trip, no full-array replace, and the whole bug class (silently discarding client-only fields on refetch) stops being possible rather than being patched per-symptom.
- Typing indicator (3 dots) while waiting for the first token, scoped precisely to the in-flight message.
- Dialogue/action/internal-monologue visually distinguished (`*action*` italic, `(monologue)` italic in a dedicated muted tone, plain dialogue normal) — plus a strengthened prompt directive (with a worked example) to stop the model putting dialogue inside asterisks.
- Regenerate button to redo the last reply; in-flight generation is properly aborted when switching characters or clearing chat.
- Collapsible debug panel showing the live structured summary state and the exact RAG hits used for the current turn.
- **Firelight design system**: sapphire-black + amber-orange theme (oklch color tokens), three font roles (Manrope sans, Cormorant Garamond serif for headings, Georgia for body text), hero + featured-row + roster home-screen layout, all fonts served locally rather than from a CDN.
- **Frontend served by the backend**: `npm run build` produces `frontend/dist/`, which FastAPI mounts directly (`/assets` static files + SPA catch-all route) — one port (8000) for both API and UI, no CORS configuration needed, works identically whether accessed via `localhost` or `127.0.0.1`. `roleplay_app/run.ps1` activates the venv and starts uvicorn in one step.
- **Real client-side routing**: added `react-router-dom` (`/` and `/chat/:characterId`) so the URL reflects which character's chat is open. This fixes a real bug — refreshing the page, or opening a link on a second device, previously always bounced to the homepage because the "which screen am I on" state lived only in memory. The backend's existing SPA catch-all already served `index.html` for any unrecognized path, so no backend change was needed — the router just started actually using that.
- **Shared social feed** (`/feed`, `feed_posts` table): characters post short in-character updates and react to each other's posts — a shared universe, not isolated per-character journals. Strictly user-triggered generation (no autonomous/scheduled posting), preserving the single-inference-slot design: a post/reaction request queues behind any in-flight chat turn (generous 300s timeout, same as the summarizer) rather than competing with it. Reactions are privacy-by-construction — the reacting character's prompt includes only the target post's public text, never the original poster's private affection/closeness/notable-facts state. Self-reaction and reacting to a comment (thread depth capped at 2 levels, enforced in application code since SQLite `CHECK` can't reference sibling rows) are both rejected server-side with a 400. Hiding a character filters their posts/reactions out of `GET /api/feed` and blocks new activity from/as them (404). `delete_character`'s existing session guard was extended to also check `feed_posts`, so a character who's only ever posted (never chatted) can't be deleted out from under a foreign-key reference. Frontend shows a dashed "ghost" post card / typing-dots comment row while a post or reaction is generating, reusing the same `TypingIndicator` component as the chat's typing state.
- **HearthSocial.ai rebrand**: renamed from the "Role·Play" wordmark to "HearthSocial" (bold serif + brand icon), with "Role-Play" and "Feed" demoted to `<h2>` section headings; renamed again shortly after to "HearthSocial.ai" once an unrelated existing repo/project was found using the plain "HearthSocial" name. Custom logo/icon assets (fireplace mark + full title-caption lockup) added; the small icon and favicon use a separately-generated 512×512/231KB variant (the original 2048×2048/4MB source stays in `public/` for other uses like the README banner) since a multi-MB icon was measurably slowing first paint by competing for the same handful of parallel HTTP/1.1 connections as the JS/CSS bundle. Note: the banner PNG itself (`hearth-social-title-caption.png`) still has "HearthSocial" (without `.ai`) baked into its pixels — the wordmark text elsewhere (page title, PWA name, in-app headers) was updated, but the graphic wasn't re-generated.
- **Dynamic portraits folder**: `frontend/public/portraits/` is genuinely runtime-writable data, not a build-time asset — the backend resolves a character's portrait by name alone (`GET /portraits/{slug}`, probing `jpg/jpeg/png/webp`), so new files dropped in or uploaded through the UI show up without a frontend rebuild. Both PNG and JPEG are accepted and never silently converted between formats (see Decisions below).
- **Avatar upload UX**: crop tool is 1:1 (matches the 1:1 thumbnail display everywhere, was previously a mismatched 3:4), client-side compressed to JPEG quality 0.85 at a fixed 500×500 output before upload, and the file picker rejects anything that isn't PNG/JPEG (both `accept` attribute and an explicit `file.type` check with an inline error message) on top of the backend's existing content-type validation.
- **Progressive Web App**: installable on both Android (Chrome) and iOS (Safari "Add to Home Screen") with a standalone (no browser chrome) launch. A shell-only service worker keeps the app icon/launch working offline-ish without ever caching API or portrait data (see Decisions below), and an `UpdateBanner` detects when a new build has actually taken over the page and offers a one-tap refresh — necessary because installed PWAs have no address bar / pull-to-refresh to fall back on.
- **First mobile breakpoint** (`@media (max-width: 600px)` in `App.css`): the chat banner (previously a fixed-height row that overflowed and overlapped the stats bar on narrow screens) now wraps properly, and the home hero shrinks its wordmark/icon/headline. Also fixed a real iOS Safari bug where tapping any input auto-zoomed the whole viewport — caused by the global `input, textarea, select` CSS rule never setting `font-size` (browsers zoom on focus for any control under 16px), fixed with one line.
- **Network resilience**: every plain JSON API call now times out after 15s instead of hanging forever on a dead connection; chat/regenerate SSE streams abort themselves after 60s of no new chunk and surface a "Connection stalled - try again" message instead of leaving the typing indicator frozen (raised from an initial 30s, which was triggering on ordinary slow-but-still-working generations on this machine's tight memory headroom, reported 2026-07-27); the chat view re-syncs session state immediately when the app is foregrounded again (in addition to its 5s poll) rather than waiting on a possibly-throttled background timer. Added defensively after reports of the installed PWA occasionally freezing, without a conclusively identified single root cause.
- **Response compression**: `GZipMiddleware` added to the FastAPI app (previously responses were sent uncompressed — the JS bundle alone was ~293KB vs. ~91KB gzipped).
- **Scene image generation** (optional, cloud, provider-swappable): a button on any assistant chat message or top-level feed post generates a scene image, built from the character's current appearance/location/mood/relationship-stage plus the actual message/post content (`character_state.build_image_prompt()`). Two providers implemented (`config.IMAGE_PROVIDER`, default `"gemini"`) - Gemini 3.1 Flash Lite Image ("Nano Banana 2 Lite") and xAI's Grok Imagine - and `image_client.py`'s public interface doesn't leak provider-specific shape, so a third provider is a contained addition, not a rewrite. The style directive (`_IMAGE_STYLE_DIRECTIVE`) is deliberately rendering-only (linework/shading/lighting) - mood and atmosphere come entirely from the character's live `character_mood` and the actual scene text, never a hardcoded tone, so a sad or tense scene doesn't get an inappropriate fixed mood tag. It also carries one fixed compositional rule: if the scene text mentions another person (e.g. the user's own roleplay persona), give them the same skin tone as the main character, since without that instruction a secondary person's appearance would render randomly (and inconsistently) on every regeneration. `_IMAGE_NEGATIVE_DIRECTIVE` was rewritten 2026-07-27 from negative phrasing ("avoid extra fingers, malformed hands...") to positive anatomy assertions ("exactly two arms, two legs, and five clearly separated fingers per hand...") - since neither Gemini's nor xAI's image APIs have a dedicated negative-prompt field, negating a noun in the one text prompt risks the autoregressive model latching onto and generating that exact noun; stating the correct anatomy directly avoids that risk.
- **Collapsible generated images**: both the chat and feed image display reuse the exact `<details>`/`<summary>` pattern already established by `ThinkingBlock.jsx` (same `.chat-reasoning` CSS class, same ▸/▾ marker) rather than inventing a new collapse widget - defaults open since you just generated it, but collapses like any other secondary content in the transcript.
- **Prompt moderation** (`routers/images.py:_neutralize_prompt()`, toggleable via `config.IMAGE_MODERATION_ENABLED`): cloud image providers generally refuse explicit sexual content, but this app's scene prompts are built straight from live roleplay chat text, which routinely is explicit. When enabled (default), the built prompt is rewritten through the *local* model (a small `llama_client.chat_completion()` call, not the cloud API) to strip explicit wording while preserving setting/character/mood, before it's ever sent to xAI. If llama-server isn't running, this fails loudly via the existing `LlamaServerUnavailable` → 503 path rather than silently falling through to send the raw prompt to the paid cloud API. Strictly user-triggered, one image per message/post (regenerating replaces it), 16:9 by default (deliberately distinct from the 1:1 used everywhere for portraits/avatars, so a generated scene doesn't read as "another avatar"). **Face consistency**: rather than plain text-to-image (`POST /v1/images/generations`), the character's existing portrait is passed as a reference image via xAI's image-*editing* endpoint (`POST /v1/images/edits`, `image_client.generate_image(..., reference_image_path=...)`), so the generated scene keeps the same face/likeness instead of a fresh random one each time; falls back to plain generation if the character has no portrait file (`shared.resolve_portrait_path()` returns `None`). This is the one deliberately non-local part of the app — local diffusion wasn't viable on this machine's RAM — gated entirely behind an unset-by-default `XAI_API_KEY`; with no key, `GET /api/health`'s `image_generation: false` keeps the buttons from even appearing, and the rest of the app is unaffected.

## Decisions & constraints worth remembering

- Single llama-server slot — summarization is "non-blocking" in the sense that the triggering turn's response is never delayed, but the very next message can queue briefly behind a summarization call. A second slot is a possible future option if memory headroom is ever confirmed comfortable.
- RAG uses a single upgraded embedding model (`bge-small-en-v1.5`) rather than a hybrid vector+keyword approach — a deliberate simplification after review.
- Declined to author one specific character concept (incest-themed backstory); Ursula was built instead with a husband-wife framing at the user's correction.
- `character_state.py` relationship stages now include user-added `spouse`, `family`, and `taboo` (beyond the original stranger/acquaintance/friend/confidant/partner), each with its own numeric gate threshold in `_STAGE_THRESHOLDS`.
- Tone/melodrama drift at high affection is treated as an **imitation problem, not an instruction-following problem**: the model tends to copy the register already present in its context (persona voice, accumulated `character_memory` prose, verbatim RAG quotes from its own past replies) more reliably than it obeys an abstract "don't use superlatives" instruction. Confirmed empirically twice — the summarizer's tone-ban and a targeted `character_state.py` directive tweak were both tested side-by-side against Kiara's real session state and produced no meaningful difference in output register. No fix has landed yet (see Known gaps); the one mechanism that reliably works for steering tone in the moment is the manual director's note, precisely because it's concrete and singular rather than one more abstract rule competing in an already-stacked prompt.
- CORS middleware was removed entirely once the frontend was consolidated onto the same origin as the API — this means the old dev workflow (separate `npm run dev` on port 5173 talking to the backend on 8000) no longer works without re-adding CORS; for frontend changes, rebuild (`npm run build`) and refresh against port 8000 instead.
- Feed posts are intentionally character-scoped, not session-scoped — the opposite lifetime from `summaries`, which resets on clear-chat by design. A character's public feed presence is meant to read as an ongoing identity that outlives any one private conversation.
- `main.py` was split into `routers/*.py` + `shared.py` once it hit 786 lines — a pure code-move (verified via `TestClient` end-to-end against every route before/after), not a behavior change. File sizes now match the rest of the codebase's norm (~100-220 lines each) instead of one file dwarfing everything else.
- **Portrait/logo image files are never silently converted or re-encoded without asking first** — established early (a PNG→JPEG batch-conversion was about to run to enable compression; stopped and reverted on correction, landing instead on "accept both PNG and JPEG, resolve by name via `/portraits/{slug}`"). Re-affirmed later even when the case for compressing was strong (6 oversized homepage PNGs measurably slowing load) — asked again rather than assuming the earlier precedent covered it, since a full backup already existing in `portraits-originals/` was itself a fact worth surfacing before acting, not a reason to skip asking.
- The service worker (`public/sw.js`) is deliberately shell-only: it never intercepts `/api/*` or `/portraits/*`, even though that means giving up offline support for actual app data. An early version's `fetch` handler intercepted everything, which (combined with the fact that a freshly-registered SW doesn't control the page that registered it, only subsequent loads) caused a real bug — hide/edit mutations stopped visibly refreshing the UI on both the phone and a laptop browser — traced to the SW's own re-`fetch()` of intercepted requests, not to HTTP caching as first suspected.
- The SW's cache-busting relies on the browser byte-diffing `sw.js` itself to detect an update — unrelated file changes (JS bundle, CSS) don't trigger re-detection on their own. Convention going forward: bump the `CACHE` version string in `sw.js` on every frontend deploy, purely to give the update-detection banner something to notice.
- PWA installability requires a secure context (HTTPS, or `localhost`) for the service worker to register at all in Chrome; a plain-HTTP LAN address like `http://192.168.1.3:8000` does not qualify, so on Android/Chrome the SW silently fails to register there (the `.catch(() => {})` on `register()` is deliberate, not an oversight) unless the device whitelists the origin via `chrome://flags/#unsafely-treat-insecure-origin-as-secure`, or the app is fronted with a real/self-signed cert. iOS Safari's "Add to Home Screen" is the exception — it doesn't require a service worker or secure context at all, just the `apple-mobile-web-app-*` meta tags, which is why it was the practical path taken for this project's actual phone.
- Local image generation was ruled out on hardware grounds (this machine's RAM is already fully committed to the text model), not a design preference — cloud is the deliberate, explicit exception to "100% local" for this one feature only, gated behind an unset-by-default API key rather than silently making the whole app dependent on the internet.
- `generated_images` uses a **deterministic** filename per message/post (`msg-{id}.jpg`, `post-{id}.jpg`) rather than a fresh UUID per generation — regenerating just overwrites the same file (no orphaned-file cleanup needed) and reuses the exact `Cache-Control: no-cache` pattern already proven for portrait re-uploads, rather than inventing a second caching strategy.
- The chat SSE stream didn't originally tell the client the new message's real database id (it only yielded content/reasoning deltas), so the image-generation button had no id to call until the client refetched the message list. First fix was a `GET /api/sessions/{id}/messages` refetch-and-replace after every turn - which caused a real regression (see "Reasoning/thinking block display" above: the refetch silently wiped `reasoning`, since that endpoint never returns it). Properly fixed by extending the SSE protocol itself: `_stream_assistant_reply()` now yields one more event, `{"type": "message_id", "message_id": <int>}`, right before `[DONE]`, straight from the row it just inserted - the same "backend synthesizes an event after its own DB write, on the already-open stream" mechanism `[DONE]` itself already used. The frontend patches that one field onto the last message directly; no refetch, no full-array replace, and the regression's whole bug class (silently discarding client-only fields) stops being possible.
- Generated scene images use the character's portrait as a reference (xAI's `/v1/images/edits`) rather than plain text-to-image, specifically because a fresh random face every generation would defeat the point — the character needs to look like *that* character. `_avatar_slug`/the portrait extension-probing loop were each previously duplicated once (in `routers/characters.py` and inline in `routers/portraits.py`); both were moved into `shared.py` as `avatar_slug()`/`resolve_portrait_path()` while wiring this up, since `routers/images.py` became a third caller of the same "character name → portrait file" resolution.
- Image generation was deliberately built provider-agnostic from the start (`config.IMAGE_PROVIDER`, `image_client.py`'s dispatch-by-provider shape) rather than hardcoding xAI throughout, since the user was explicit this shouldn't be locked to one vendor. Initially only the seam was built (no second provider implemented, to avoid guessing an unverified API shape) - Gemini was added once the user actually decided to use it, at which point its real REST shape was looked up (Google's official docs) rather than assumed. `IMAGE_PROVIDER` defaults to `"gemini"` now, reflecting that decision; `xai` is still fully implemented and selectable.
- Gemini's REST shape needed extra verification care: search results and one `WebFetch` both described a `POST /v1beta/interactions` endpoint with an `input` array, which is *not* the long-standing `models/{model}:generateContent` shape Gemini has historically used - unusual enough to be worth double-checking rather than trusting on one fetch. A follow-up fetch of `ai.google.dev/api/generate-content` confirmed Google's own docs state "The Interactions API is now generally available" and is the recommended endpoint for newer capabilities like image generation, which is what `_generate_gemini()` targets.
- Switched from the full Gemini 2.5 Flash Image model to Nano Banana 2 Lite (`gemini-3.1-flash-lite-image`) plus a pinned `1K` `image_size`, purely for cloud cost control (explicit user concern about bill size) — this is also, conveniently, the Lite model's *only* supported resolution (2K/4K aren't available on it per Google's model page), so there was no lower-cost tier being left on the table.
- Gemini's native multimodal generation returns a text response alongside the image by default (unlike xai's dedicated image-only endpoints), wasting output tokens on commentary the app throws away anyway. No documented API field exists to hard-disable this on the Interactions API, so `_generate_gemini()` instead appends a plain-language instruction to the prompt asking for image-only output - a soft nudge, not a guarantee, since there's no strict modality flag to enforce it.
- Both providers' reference-image path append a fixed `_REFERENCE_IMAGE_INSTRUCTION` telling the model to take only the character's face/likeness from the portrait and ignore its background - without this, models tend to carry the portrait's own background into the new scene instead of the location actually described in the prompt.
- Added `_IMAGE_NEGATIVE_DIRECTIVE` (`character_state.py`) after a real generation gave a secondary/side character bad anatomy - checked both providers' docs first and confirmed neither exposes a dedicated `negative_prompt` field (both are autoregressive/multimodal models, not diffusion, so classic CFG-style negative prompting doesn't apply there); the practical equivalent is stating avoidances directly in the text prompt, same mechanism as every other fixed directive in this file. Explicitly scoped to "every person in the scene, not only the main character," since the main character already has a reference image anchoring its proportions - secondary characters don't, which is exactly where the anatomy errors showed up.
- Prompt moderation runs through the *local* model, not a word/phrase blocklist and not a second cloud call — reuses infrastructure that's already there (`llama_client.chat_completion()`), costs nothing extra, and handles arbitrary phrasing rather than a fixed list that would always be one step behind. It intentionally has no silent fallback: if it can't run (llama-server down), the request fails rather than quietly sending an un-neutralized prompt to the paid cloud API.

## Known gaps

- `CharacterForm.jsx`'s `STAGES` constant (used for the "starting relationship stage" dropdown) still only lists `stranger/acquaintance/friend/confidant/partner` — `spouse`, `family`, and `taboo` can't be picked as a *starting* stage from the UI (they're only reachable via the summarizer advancing into them over time). `theme.js`'s `STAGE_LABELS` is missing a `taboo` entry too (falls back to showing the raw string, not broken, just unstyled). Neither has been fixed yet.
- Melodrama/purple-prose drift at high affection/spouse-tier: confirmed real via side-by-side generation testing, no working fix landed (tone-ban instruction and directive-tweak both failed empirically). Next candidates to try: a few-shot example embedded in the prompt (imitation-based, not instruction-based), or reversing the sampling nudge that currently *increases* `top_p` at affection≥70.
- Mobile responsiveness: now verified on an actual phone (iPhone, Safari) and has exactly one `@media (max-width: 600px)` breakpoint covering the chat banner and home hero — real problems there were found and fixed, but coverage elsewhere (modals, character grid, feed page) still relies only on the pre-existing fluid/`vw`-capped layout and hasn't been specifically tuned or verified.
- The installed PWA has been reported to occasionally freeze / drop its connection to the backend, intermittently and without a conclusively identified trigger (backgrounding vs. WiFi drop vs. iOS suspending the WKWebView were all considered). Mitigated with client-side timeouts, stream-stall detection, and foreground re-sync (see Decisions above), but the underlying cause was never isolated, so it's a mitigation, not a confirmed fix.
- Must run uvicorn as a single worker (the summarizer's in-memory concurrency guard is process-local).
- Behavior-directive band thresholds are a starting point, not tuned against real play.

## Verified so far

- llama-server loads and responds correctly at the configured flags (health check, `/v1/models`, `/tokenize`).
- `sqlite-vec` KNN query syntax confirmed empirically (both the working form and the exact `JOIN`-breaks-it bug that shipped once and was fixed).
- Embedding model loads fully offline once cached (timed, no network calls).
- Character creation, opening-scene generation, chat streaming, clear-chat archiving, avatar upload/crop, hide/unhide (both characters and sessions, including a fixed refresh bug where unhidden sessions didn't reappear until reload), and the director's note (including a fixed bug where a note-only submission with no message silently did nothing) have all been exercised end-to-end.
- Anti-drift enforcement observed directly on Kiara's real session: a summarization cycle showed closeness moving exactly +10 (the delta cap engaging, not an unbounded jump) and affection correctly clamped at the 0–100 ceiling.
- The affection-directive tweak for reducing melodrama was tested via a real side-by-side generation comparison against Kiara's actual state (same test message, old vs. new directive text) — confirmed to make no meaningful difference, ruling it out rather than shipping it on faith.
- Feed backend verified in isolation: the `feed_posts` `CHECK` constraint was confirmed to reject a mismatched `author_type`/`character_id` row directly against a live `db.get_db()` connection; `npm run build` and `npm run lint` are clean for the new frontend components.
- The `main.py` → `routers/*.py` split was verified route-by-route with `TestClient` (every endpoint dispatches correctly post-refactor) before being considered done, not just "it imports."
- `GZipMiddleware` confirmed actually compressing (`Content-Encoding: gzip` present on a `TestClient` response with `Accept-Encoding: gzip`).
- The PWA has been installed and used on a real iPhone via Safari's "Add to Home Screen" (standalone launch, custom icon, no browser chrome) — real bugs were found this way that wouldn't have surfaced in a desktop browser: the chat banner overflow/overlap on narrow screens, the iOS input-auto-zoom bug, hide/edit not refreshing the UI (traced to the service worker's fetch interception, not HTTP caching), and avatar re-uploads not showing up (missing cache-control on the portrait route).
- Image generation routes verified end-to-end with `TestClient` against real message/feed-post rows (not just route registration): both return a clean 503 with the exact "no XAI API key configured" detail when `XAI_API_KEY` is unset, proving the character-load → state-lookup → prompt-build pipeline runs correctly right up to the actual xAI call. `GET /api/sessions/{id}/messages` and `GET /api/feed` were re-checked afterward and correctly carry the new `id`/`image_path` fields without breaking their existing shape.

## Not yet fully verified

- Long-run behavior of the affection/closeness mechanic over many real messages beyond what's been spot-checked so far.
- Whether reversing the high-affection `top_p` sampling nudge actually reduces melodramatic word choice — flagged as a next experiment, not yet run.
- Whether the PWA freeze/dropped-connection mitigations (timeouts, stall detection, foreground re-sync) actually eliminate the reported freezing, or just make it recover faster — not enough real-world PWA usage yet to confirm either way.
- PWA installability/update flow over Chrome specifically (Android or desktop) hasn't been exercised — verification so far is iOS Safari only, which has a looser (no secure-context, no service-worker-required) install path than Chrome's.
- Feed post/reaction generation has not yet been exercised live end-to-end against a running llama-server — the verification checklist in the addendum plan (no-active-session fallback, tone reflecting live affection/mood, reaction privacy, self-react/comment-react 400s, hide filtering, delete guard, queuing behind a live chat turn) is still outstanding.
- Image generation has not yet been exercised against the real xAI API (no `XAI_API_KEY` was set during development/verification, by design - real calls cost money and need a real key the assistant doesn't have). Everything up to the API call itself is verified (see above); the actual `generate_image()` HTTP call, the resulting image quality/prompt tuning, and whether `build_image_prompt()`'s heuristic actually produces good results all need a real key and manual testing to confirm.
- The `/v1/images/edits` reference-image path specifically is unverified against a real call: xAI's own docs don't fully specify whether `response_format` is honored on that endpoint, so `image_client.py`'s defensive `b64_json`-then-`url` fallback is untested against real response bytes. Whether the returned scene actually preserves the character's face/likeness (the entire point of using this endpoint over plain generation) also hasn't been confirmed with a real image.
- Gemini (`_generate_gemini()`) is entirely unverified against a real call - no `GEMINI_API_KEY` was available during development. The Interactions API endpoint, request shape (`input` array), and response-parsing path (`steps[].content[].data` for `model_output` blocks) are all based on Google's documentation as fetched during this session, not a real response payload. If the actual response shape differs even slightly (e.g. a different step `type` string, or a different field name than `data`), `_extract_gemini_image_bytes()` will raise `ImageGenerationUnavailable("Gemini response contained no image data")` rather than silently returning garbage - but it needs a real key to actually confirm the happy path works.
- Prompt moderation (`_neutralize_prompt()`) has only been verified for its two failure/bypass paths (llama-server down → 503; toggled off → skips straight to the provider check) via `TestClient`. Whether the local model's rewrite actually neutralizes explicit content well enough for xAI to accept the prompt - the entire reason this exists - needs a real llama-server running and a real API key to confirm.
